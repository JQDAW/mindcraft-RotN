# `@mindcraft-rotn/rotn-data`

RotN 3.3.4 facts (ADR 0005) and two-way name translation between Minecraft 1.12.2 and the 1.21-style names Mindcraft uses. rotn-data brief deliverables 2 and 3.

## API (`packages/rotn-data/index.js`, ESM)

### Name translation

| Call | Result |
| --- | --- |
| `toNew(oldName, meta = 0)` | `'log', 1` / `'log:1'` / `'minecraft:log:1'` → `'spruce_log'`; `'coal', 1` → `'charcoal'`; modded names pass through: `'pyrotech:rock', 6` → `'pyrotech:rock:6'` (`:0` omitted) |
| `toOld(newName)` | `'oak_log'` → `{ name: 'minecraft:log', meta: 0 }`; `'pyrotech:rock:6'` → `{ name: 'pyrotech:rock', meta: 6 }`. `name` is always the full registry name. Old spellings (`'log:2'`) are accepted too. |
| `blockToNew(oldName, meta)` | block states: `'log', 4` (axis x) → `'oak_log'`; `'lit_furnace', 3` → `'furnace'` |
| `blockToOld(newName)` | every state: `'oak_log'` → `log:0`, `log:4`, `log:8` |
| `registryName(entryOrName)` | `{ name: 'stone' }` (bot.registry) → `'minecraft:stone'`; `'pyrotech:rock'` unchanged |

- **Anything that cannot be mapped is `null`** (or `[]` for `blockToOld`): never a guess, a number or "unknown".
- Modded names are checked against the names the 3.3.4 server syncs, so a typo gives `null`.
- Damageable items keep their name whatever the damage: `toNew('stone_pickaxe', 17)` → `'stone_pickaxe'`.
- Blocks are strict: `blockToNew` gives `null` for a metadata the block does not have (`blockToNew('stone', 7)`). It uses the item table only for names that have no block states.
- Vanilla table: `vanilla/flattening-items.json` (643 item pairs, a bijection). `spawn_egg` is left out because its mob is in NBT, and `stone_slab:2` (petrified oak slab) is added. `tallgrass:0` (the shrub item) stays `null` on purpose: its 1.13 name `dead_bush` is already `deadbush`'s. Every synced `minecraft:` item is covered except `air`, `portal`, `end_portal`, `end_gateway` and `spawn_egg`.
- Block table: `vanilla/flattening-blocks.json` (1682 states).
- Both tables come from minecraft-data's `pc/common/legacy.json` and `pc/1.12.2`, with every 1.12 name checked against the 3.3.4 server's registry (minecraft-data's `light_gray_glazed_terracotta` and `light_gray_shulker_box` blocks are `silver_*` there), and the later renames carried forward to 1.21 (`rose_red` → `red_dye`, `sign` → `oak_sign`, `grass` → `short_grass`, `grass_path` → `dirt_path`, 1.13's `stone_slab` → `smooth_stone_slab`). Rebuild with `node packages/rotn-data/tools/build-flattening.mjs`.

### Catalog

`loadRotnData('3.3.4')` returns the pack's catalog; the same calls are exported bound to 3.3.4. Inputs may be registry names, old names with metadata, 1.21 names or bot.registry entries.

| Call | Result |
| --- | --- |
| `getBlock(name)` | the dumped block with `states` and the selected `state`, or `{ name, propertiesKnown: false }` before a dump, or `null` if the server has no such block |
| `getItem(name)` | the dumped item with its `variant` for the metadata |
| `harvestInfo(block, meta?)` | `{ block, meta, hardness, tool, level, levelName, toolRequired, material }`; `levelName` is Tool Progression's (`0` Crude, `1` Sturdy, ...); `null` without a dump |
| `recipesFor(item, { meta })` | crafting-grid recipes after CraftTweaker, shaped like prismarine-recipe but keyed by names: `{ id, type, result {name, meta, count}, requiresTable, inShape \| ingredients, mirrored?, remaining? }`, ingredient = `{ stacks: [{name, meta}], ore? }` (ore dictionary expanded; meta `32767` = any) |
| `smeltingFor(item)`, `smeltingOf(input)` | furnace recipes by output or by input |
| `entity(name)`, `entityByModId(modId, typeId)`, `modEntityTable()` | entity facts; the mod-local table maps FML EntitySpawn ids to registry names. `modEntityTable()` gives net-forge's shape `{ [modId]: { [modEntityTypeId]: registryName } }` (entries with `modSpawn: true`) |
| `stateMetaRemap()`, `clientMeta(block, idMeta)`, `networkRemap(blockIds)` | network block-state ids whose metadata is not `id & 15` (`state-meta-remap.json`, dumper 0.2.0; for forge-bridge). Forge's second `BLOCK_STATE_IDS` pass sends the double plant's upper half as `175 << 4 \| 11`, but a Forge client and `/testforblock` report meta 10. `stateMetaRemap()` gives `{ encoding, records: [{networkId, block, blockId, idMeta, stateMeta, stateNetworkId, state}], byBlock: { [block]: { [idMeta]: stateMeta } }, scanned, anomalies }`. `clientMeta('minecraft:double_plant', 11)` is 10; a meta that is not remapped comes back unchanged. `networkRemap({ [registryName]: id })` builds `Map<networkId, clientMeta>` (remapped ids only) from the connected server's block ids, because `records[].networkId` uses the test server's. All three return `null` until a dump has the table (nothing is guessed); the stub is `test/fixtures/mini-dump/state-meta-remap.json` |
| `isDangerous(name)`, threat fields on `entity()` | `imob` (the dump: the class implements IMob), `targetsPlayers` (bytecode-cited, `3.3.4/entity-overrides.json`), `hostile` = `imob \|\| targetsPlayers`, `dangerous` (avoid rather than fight: Ice and Fire dragons, sea serpent, death worm, cockatrice), `threat {confidence, evidence, note}`. Every override cites the mod jar, class and AI task; mobs reviewed and not marked (e.g. myrmex, which target `EntityLiving` only) are listed with the reason |
| `isReplaced(name)`, `entity().replacedBy` | vanilla animals another mod removes on this pack: Animania replaces `minecraft:chicken`, `cow`, `pig`, `rabbit` and `sheep` (`config/animania.cfg`, `replaceVanilla*=true`; horses stay). `replacedBy` lists the replacing breeds from the dump. `common-mobs.json` leaves these out (G2 batch 1: the server refused to summon them) |
| `lookup(query, { limit, kind })` | fuzzy search over registry names, 1.21 aliases and display names, for `!lookup` |
| `installRecipes(registry, { maxVariants })` | replaces `registry.recipes`' contents, **in place**, with the dump's crafting recipes in minecraft-data's format, keyed by that registry's (the connected server's) item ids, so mineflayer's `bot.recipesFor`/`bot.craft` and Mindcraft's `getItemCraftingRecipes`/`getDetailedCraftingPlan` use RotN recipes, not minecraft-data's vanilla 1.12.2 ones (`src/utils/mcdata.js` `installRotnRecipes()`). In place because prismarine-recipe keeps a reference to the object from when the bot was created. Each dump recipe becomes one variant per choice of stack, because a minecraft-data slot holds one `{id, metadata}` and an ore dictionary ingredient lists many. Equal ingredients take the same stack (single-kind variants, exactly as before, first), and, when an ingredient fills several slots, mixes of its likeliest stacks follow in the room the cap leaves (multisets within a budget of 64, ordered by cost; a mix never pairs a wildcard with a specific meta of the same item, which would count one stack twice). #145 and #152 reviews: mineflayer fills each slot with one `{id, metadata}`, so 3 rock slots from one variant would need 3 rocks of one kind, while the server accepts any rock per slot. Variants are ordered likeliest first (`pyrotech:`, then `minecraft:`, then other mods) and capped at 256 per recipe (`truncated` in `stats()`). They are built lazily per result id. Wildcard metadata becomes `null` (any). Skipped: dynamic recipes, `matchesSample: false`, NBT stacks, unknown items, and variants that take the result itself (ore dictionary conversions). Returns `{ results, recipes, resultNotInRegistry, stats() }`. RotN 3.3.4: 3,666 result ids from 6,089 recipes, about 0.3 s, and 115,782 variants if every one is built (209 recipes truncated; counted after #152's mixed variants) |
| `howToGet(item, { meta })`, `formatHowToGet(result, { maxWays })` | every way to get an item, as `{ item: {name, meta}, ways }`, or `null` for an unknown item. The ways come in this order: (1) **world rules** from `3.3.4/world-sources.json` (`kind: 'world'`: break a rock pile, mine stone with a pickaxe below Sturdy for 4 rocks, break leaves for sticks, fell a tree, debark a placed log, a plank from the debarked log, ores, the start kit), each with `blocks`, `tool`, `count`, `confidence` (`documented` or `inferred`), `evidence` and `unverified`. Rules with an `ore` (rock piles, stone for rocks: `rock`) also give `ore: { name, members, blocks: [{ name, metas }] }`, the block metas whose drop is in that ore dictionary, and `inOre` on each listed block with a meta: a bare `pyrotech:rock` pile also covers metas 4, 5, 7 and 9 (clumps and piles, not rocks); (2) **crafting** (`kind: 'craft'`: `requiresTable`, `gives`, `inputs: [{count, ore, choices (likeliest first, at most 6), more}]`, likeliest first, duplicates dropped); (3) **furnace smelting** (`kind: 'smelt'`); (4) the dump's **plain block drops** (`kind: 'block-drop'`, `confidence: 'dump-sample'`: `getItemDropped` with a fixed seed, without event-handler or random drops, and without blocks a world rule covers). Stone-to-rock pairs come from the dumped names (stone state `variant` or `type` = rock display name minus ' Rock'): `minecraft:stone:0` -> `pyrotech:rock:0` is documented; the vanilla variants and the Underground Biomes stones (the stone at the G3 spawn) are `inferred`. `formatHowToGet` gives a short plain-text answer for chat or a prompt |
| `canFill(recipe, stacks, { times })` | whether inventory stacks (`{ name, meta or metadata, count }`; bot names like `stick` or full names) can fill a recipe, a recipe id or a `howToGet` craft way (`recipeId`). Each slot accepts any stack its ingredient lists (wildcard = any meta; NBT stacks not matched), slots are independent, and slots are matched to item units, so one item is never counted twice. Returns `{ ok, missing, assignment, recipeId }`, or `null` for an unknown recipe. The rule rotn-data's recipe variants use, for skills-rotn (#152 review). Also `recipeById(id)` |
| `rockRecipes()` | every "4 identical rocks -> block" recipe as `{ rock, gives, recipeId }` (35 on 3.3.4): stone rock -> `minecraft:cobblestone`, limestone rock -> `contenttweaker:limestone_cobble`, sandstone rock -> `minecraft:sandstone`, Underground Biomes rocks -> their cobble. For the G3 "rocks to cobblestone" check, which accepts every output |
| `threatOf(entity)`, `nightThreats({ biome, limit })`, `NIGHT_THREATS_NOT_REFLECTED` | first-night threats. `threatOf` gives `{ name, displayName, level, reaction, source, rule?, summary, explodes, ranged, evidence }`, or `null` for an unknown entity. `level` is `dangerous` (entity-overrides.json), `hostile` (IMob or bytecode-cited player targeting) or `none`. `reaction` is `fight`, `keep-distance`, `take-cover`, `avoid`, `ignore-unless-provoked` or `ignore`. First match wins: a dangerous mob is always `avoid` (`source: 'override'`); then an entry in `3.3.4/threat-reactions.json` (zombie, skeleton, spider, creeper and Fire Creeper documented from the research's hazard table; enderman, witch, illusion illager, guardian, vindicator and slime `vanilla`; Charm's spectre (with the pack's `config/charm.cfg`: its touch curses items), Quark's ashen and dweller, Ice and Fire's dread lich and troll, the Iceologer, Mowzie's naga, the Rats illager piper, ten Ancient Beasts mobs, and the last 14 overworld night defaults (Fish's Undead Rising's mushroom and frozen zombies, mummy and sludge lord; Defiled Lands' host, scuttler and two shamblers; Mowzie's grottol, foliaath and barakoana; Better Animals Plus' tarantula), and the research's parasite and weta (Fish's Undead Rising; the parasite latches onto a player who touches it, and bursts from dead zombie hosts or from desert sand; the weta only retaliates and does not spawn naturally on this pack) `verified` from each mod's bytecode in the pinned pack, citing jar, class and methods, and for the troll and the 14 the pack's configs (`config/ice_and_fire.cfg`, `roughmobsrevamped.cfg`, ...); husk and zombie villager `vanilla`, with the configs that treat them like the zombie. What could not be settled is in the evidence as "Not settled: ..."); then, for hostile mobs, a class rule on the dumped class's simple name (`source: 'inferred'`: every creeper variant keeps distance and counts as exploding, skeleton and stray variants take cover; wither skeletons excluded); then a default (hostile → `fight`, otherwise `ignore`). **Gap:** `threatOf` takes the registry name only, so a custom name that changes behaviour (an Animania rabbit named "Killer" targets players) is not reflected. `nightThreats` lists the hostile mobs in a biome's (or, by default, every overworld biome's) `monster` spawn list, with `share` of the spawn weight, most likely first. What it does not reflect is exported as `NIGHT_THREATS_NOT_REFLECTED`: the Special Mobs variants (they replace vanilla mobs at spawn time, so they are in no spawn list), light level, Mob Stages, invasions and hordes, and MultiMob's lists (no biome filter; plains lists ghasts) |

## Data (`3.3.4/`)

| File | Source |
| --- | --- |
| `registry-names.json` | every block, item, entity, biome, enchantment and potion name the real 3.3.4 server synced, from net-forge's G1 Batch A RegistryData capture (`packages/forge-bridge/test/fixtures/rotn-3.3.4/handshake-runA.*`). Rebuild: `node packages/rotn-data/tools/registry-from-capture.mjs`. Numeric ids are kept for reference only. |
| `mining-levels.json` | `config/tool_progression/mining_level_names.cfg` from the pinned zip |
| `manifest.json`, `blocks.json`, `items.json`, `recipes.json`, `smelting.json`, `oredict.json`, `entities.json`, `spawns.json`, `serializers.json`, `state-meta-remap.json` | the dump (ADR 0004, `tools/dumper/README.md`): the third RotN 3.3.4 dump (dumper 0.2.0, the state-meta-remap batch; it replaced the second), 2026-11-02, dumper jar SHA-256 in `manifest.json`. `blocks`, `items`, `recipes` and `spawns` are stored as `.json.br`. Known harvest gaps are pinned in `test/fixtures/harvest-known-gaps-3.3.4.json`. |
| `common-mobs.json` | mobs most likely met in the overworld, from `spawns.json` (`tools/build-common-mobs.mjs`); harness-ops' G2 mob scenario reads `mobs[].name` |
| `world-sources.json` | hand-written non-recipe ways to get items (for `howToGet`), from `docs/research/rotn-progression.md` (which cites the RotN wiki, the handbook and the pinned pack's scripts and configs) and the G2 batches. Each rule has `evidence`, a `confidence` and an `unverified` list for the G3 harness to check; `test/howto.test.js` checks that every name and meta in it exists on the server and in the dump |
| `threat-reactions.json` | hand-written reactions to first-night mobs (for `threatOf`): `entities` from `docs/research/rotn-progression.md` section 2 (hazard table) plus `vanilla` entries and `verified` entries read from the mods' bytecode (javap on the pinned pack's jars; no mod code run), and `classRules` (creeper and skeleton variants, matched on the dumped class name, inferred; Special Mobs enderman and witch variants, `inferred`: only their vanilla targeting AI is verified from the mod's bytecode, and each variant's extra behaviour (the thief enderman teleports its target, the domination witch pulls its target in, ...) is in the rule's `variants` and returned as `variantNote`; each rule with a note on its limits); `test/threats.test.js` checks that every entity exists, that `documented` entries cite the research, and that no creeper class in the dump gets `fight` |

Import a fetched dump with `node packages/rotn-data/tools/import-dump.mjs <fetched rotn-dump dir> --jar-sha256 <SHA-256 of the dumper-build artifact>`. The importer refuses a manifest whose `dumperJar.sha256` differs, and records the SHA-256 of every raw fetched file in `manifest.import.rawSha256`. Files over 1 MiB are stored as `.json.br`. It also refuses a dump:

- without its `DONE` marker;
- without one of the dump files (`serializers.json` and `state-meta-remap.json` included, so a dump from dumper 0.1.0 cannot be imported as is);
- with a `state-meta-remap.json` record that is not consistent (`networkId = blockId << 4 | idMeta`, metas 0-15 that differ, one record per id, a synced block), or with remap anomalies (`--allow-errors` overrides those). A `blockId` that differs from the registry capture is only printed as a note, because the table is used by block name;
- with dumper errors or dropped entries (`manifest.entryErrors`; `--allow-errors` overrides both);
- with another Forge build;
- with names that differ from the registry capture;
- without the early-game recipes from the pack's scripts (`test/fixtures/scripts-3.3.4-early-recipes.json`, transcribed from the zip with file and line).

## Tests

`npm test` runs `packages/rotn-data/test/*.test.js`, all offline:

- `translate.test.js`: every vanilla item round-trips; all names in `rotn-progression.md` section 4 resolve both ways; generated files are up to date.
- `catalog.test.js`: the API on a synthetic mini dump (`test/fixtures/mini-dump`, values made up).
- `import-dump.test.js`: the importer's checks.
- `acceptance-3.3.4.test.js`: the brief's acceptance tests on the real dump (crude axe, Crafting Tools, crafting table, rocks to cobblestone, stone pickaxe and axe recipes match the scripts; `harvestInfo('stone')`; harvest info for every block state; the mod-local entity table is complete). They skip only when no dump is imported.
