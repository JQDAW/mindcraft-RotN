# `@mindcraft-rotn/rotn-data`

RotN 3.3.4 facts (ADR 0005) and two-way name translation between Minecraft 1.12.2 and the 1.21-style names Mindcraft uses. rotn-data brief deliverables 2 and 3.

## API (`packages/rotn-data/index.js`, ESM)

### Name translation

| Call | Result |
| --- | --- |
| `toNew(oldName, meta = 0)` | `'log', 1` / `'log:1'` / `'minecraft:log:1'` → `'spruce_log'`; `'coal', 1` → `'charcoal'`; modded names pass through: `'pyrotech:rock', 6` → `'pyrotech:rock:6'` (`:0` omitted) |
| `toOld(newName)` | `'oak_log'` → `{ name: 'minecraft:log', meta: 0 }`; `'pyrotech:rock:6'` → `{ name: 'pyrotech:rock', meta: 6 }`. `name` is always the full registry name. Old spellings (`'log:2'`) are accepted too. |
| `blockToNew(oldName, meta)` | block states: `'log', 4` (axis x) → `'oak_log'`; `'lit_furnace', 3` → `'furnace'` |
| `blockToOld(newName)` | every state: `'oak_log'` → `log:0`, `log:4`, `log:8` |
| `registryName(entryOrName)` | `{ name: 'stone' }` (bot.registry) → `'minecraft:stone'`; `'pyrotech:rock'` unchanged |

- **Anything that cannot be mapped is `null`** (or `[]` for `blockToOld`): never a guess, a number or "unknown".
- Modded names are checked against the names the 3.3.4 server syncs, so a typo gives `null`.
- Damageable items keep their name whatever the damage: `toNew('stone_pickaxe', 17)` → `'stone_pickaxe'`.
- Blocks are strict: `blockToNew` gives `null` for a metadata the block does not have (`blockToNew('stone', 7)`). It uses the item table only for names that have no block states.
- Vanilla table: `vanilla/flattening-items.json` (643 item pairs, a bijection). `spawn_egg` is left out because its mob is in NBT, and `stone_slab:2` (petrified oak slab) is added. `tallgrass:0` (the shrub item) stays `null` on purpose: its 1.13 name `dead_bush` is already `deadbush`'s. Every synced `minecraft:` item is covered except `air`, `portal`, `end_portal`, `end_gateway` and `spawn_egg`.
- Block table: `vanilla/flattening-blocks.json` (1682 states).
- Both tables come from minecraft-data's `pc/common/legacy.json` and `pc/1.12.2`, with every 1.12 name checked against the 3.3.4 server's registry (minecraft-data's `light_gray_glazed_terracotta` and `light_gray_shulker_box` blocks are `silver_*` there), and the later renames carried forward to 1.21 (`rose_red` → `red_dye`, `sign` → `oak_sign`, `grass` → `short_grass`, `grass_path` → `dirt_path`, 1.13's `stone_slab` → `smooth_stone_slab`). Rebuild with `node packages/rotn-data/tools/build-flattening.mjs`.

### Catalog

`loadRotnData('3.3.4')` returns the pack's catalog; the same calls are exported bound to 3.3.4. Inputs may be registry names, old names with metadata, 1.21 names or bot.registry entries.

| `playerCollision(name)` | what a player collides with in that block state (net-forge #259): `{ boxes, varies, source }`. For foods a script sets more than once, `scriptWon` names the line that won per field |
| `harvestInfo(block, meta?)` | `{ block, meta, hardness, tool, level, levelName, toolRequired, material }`; `levelName` is Tool Progression's (`0` Crude, `1` Sturdy, ...); `null` without a dump |

| `smeltingFor(item)`, `smeltingOf(input)` | furnace recipes by output or by input |
| `entity(name)`, `entityByModId(modId, typeId)`, `modEntityTable()` | entity facts; the mod-local table maps FML EntitySpawn ids to registry names. `modEntityTable()` gives net-forge's shape `{ [modId]: { [modEntityTypeId]: registryName } }` (entries with `modSpawn: true`) |

| `lookup(query, { limit, kind })` | fuzzy search over registry names, 1.21 aliases and display names, for `!lookup` |
| `installRecipes(registry, { maxVariants })` | replaces `registry.recipes`' contents, **in place**, with the dump's crafting recipes in minecraft-data's format, keyed by that registry's (the connected server's) item ids, so mineflayer's `bot.recipesFor`/`bot.craft` and Mindcraft's `getItemCraftingRecipes`/`getDetailedCraftingPlan` use RotN recipes, not minecraft-data's vanilla 1.12.2 ones (`src/utils/mcdata.js` `installRotnRecipes()`). In place because prismarine-recipe keeps a reference to the object from when the bot was created. Each dump recipe becomes one variant per choice of stack, because a minecraft-data slot holds one `{id, metadata}` and an ore dictionary ingredient lists many. Equal ingredients take the same stack (single-kind variants, exactly as before, first), and, when an ingredient fills several slots, mixes of its likeliest stacks follow in the room the cap leaves (multisets within a budget of 64, ordered by cost; a mix never pairs a wildcard with a specific meta of the same item, which would count one stack twice). #145 and #152 reviews: mineflayer fills each slot with one `{id, metadata}`, so 3 rock slots from one variant would need 3 rocks of one kind, while the server accepts any rock per slot. Variants are ordered likeliest first (`pyrotech:`, then `minecraft:`, then other mods) and capped at 256 per recipe (`truncated` in `stats()`). They are built lazily per result id. Stone-to-rock pairs come from the dumped names (stone state `variant` or `type` = rock display name minus ' Rock'): `minecraft:stone:0` -> `pyrotech:rock:0` is documented; the vanilla variants and the Underground Biomes stones (the stone at the G3 spawn) are `inferred`. `formatHowToGet` gives a short plain-text answer for chat or a prompt |
| `canFill(recipe, stacks, { times })` | whether inventory stacks (`{ name, meta or metadata, count }`; bot names like `stick` or full names) can fill a recipe, a recipe id or a `howToGet` craft way (`recipeId`). Returns `{ ok, missing, assignment, recipeId }`, or `null` for an unknown recipe. The rule rotn-data's recipe variants use, for skills-rotn (#152 review). Also `recipeById(id)` |
| `rockRecipes()` | every "4 identical rocks -> block" recipe as `{ rock, gives, recipeId }` (35 on 3.3.4): stone rock -> `minecraft:cobblestone`, limestone rock -> `contenttweaker:limestone_cobble`, sandstone rock -> `minecraft:sandstone`, Underground Biomes rocks -> their cobble. What it does not reflect is exported as `NIGHT_THREATS_NOT_REFLECTED`: the Special Mobs variants (they replace vanilla mobs at spawn time, so they are in no spawn list), light level, Mob Stages, invasions and hordes, and MultiMob's lists (no biome filter; plains lists ghasts) |
| `mobDigging(entity)`, `canMobDig(entity, block, { meta, held })` | digging mobs (Epic Siege Mod 13.169 + ESM-Tweaks 0.4.5 + Tool Progression, from `3.3.4/mob-digging.json`). `mobDigging` gives `{ name, digs, requiresTools, reach, keepWithin, when, confidence }`, or `null` for a mob that does not dig. `canMobDig` gives `{ canDig, byHand, needs: {type, minLevel} or null, ticksByHand, reason }`, or `null` for a non-digger or an unknown block. `held` is the tool classes the mob holds (`[{ type, level }]`, either hand). Import a fetched dump with `node packages/rotn-data/tools/import-dump.mjs <fetched rotn-dump dir> --jar-sha256 <SHA-256 of the dumper-build artifact>`. The importer refuses a manifest whose `dumperJar.sha256` differs, and records the SHA-256 of every raw fetched file in `manifest.import.rawSha256`. Files over 1 MiB are stored as `.json.br`. It also refuses a dump:

- without its `DONE` marker;
- without one of the dump files (`serializers.json` and `state-meta-remap.json` included, so a dump from dumper 0.1.0 cannot be imported as is);
- with a `state-meta-remap.json` record that is not consistent (`networkId = blockId << 4 | idMeta`, metas 0-15 that differ, one record per id, a synced block), or with remap anomalies (`--allow-errors` overrides those). A `blockId` that differs from the registry capture is only printed as a note, because the table is used by block name;
- with dumper errors or dropped entries (`manifest.entryErrors`; `--allow-errors` overrides both);
- with another Forge build;
- with names that differ from the registry capture;
- without the early-game recipes from the pack's scripts (`test/fixtures/scripts-3.3.4-early-recipes.json`, transcribed from the zip with file and line).

## Tests

`npm test` runs `packages/rotn-data/test/*.test.js`, all offline:

- `translate.test.js`: every vanilla item round-trips; all names in `rotn-progression.md` section 4 resolve both ways; generated files are up to date.
- `catalog.test.js`: the API on a synthetic mini dump (`test/fixtures/mini-dump`, values made up).
- `import-dump.test.js`: the importer's checks.
- `acceptance-3.3.4.test.js`: the brief's acceptance tests on the real dump (crude axe, Crafting Tools, crafting table, rocks to cobblestone, stone pickaxe and axe recipes match the scripts; `harvestInfo('stone')`; harvest info for every block state; the mod-local entity table is complete). They skip only when no dump is imported.
